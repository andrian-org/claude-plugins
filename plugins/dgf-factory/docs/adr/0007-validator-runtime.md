# 0007 — Validators run on Python with lxml and jsonschema

[ADR 0006](0006-process-verification-revised.md) §3 says validation runs *in-process*
against vendored schemas. It does not say which process. Roadmap milestone 8 cannot write a
validator until that is decided, because the two candidate standard libraries cannot do the
job on their own.

## Context

Read on **2026-09-23**. DGF paths are relative to the DGF repository root at `aa1d5c4c2`.

### Neither standard library validates either family

- Python's standard library has **no XSD validation** and **no JSON Schema validation**.
  `xml.etree` parses XML but has no schema support.
- Node's standard library has neither either.
- The two scripts this plugin already ships are stdlib-only:
  `skills/dgf-doctor/scripts/doctor.py` and `scripts/check_knowledge_stamps.py` import
  nothing outside the standard library.
- On the machine this was read on, `python3` is **3.9.6** (the macOS system interpreter)
  with neither `lxml` nor `jsonschema` installed. `node` is v26 and the .NET 10 SDK is present.

### A plugin cannot install its own dependencies

The Claude Code plugin format has no dependency-install step. The `plugin-structure` skill's
guidance is to *"document dependencies: list required tools and versions"*
(`.claude/skills/plugin-structure/SKILL.md`, §Portability). So any third-party dependency
must be installed by the user, and the plugin must detect when it is missing.

### The XSD family: libxml2 compiles 8 of 9 vendored XSDs

Each file under `knowledge/schemas/xsd/` was compiled with `xmllint` (libxml2 2.9.13, the
engine `lxml` wraps):

- `form`, `grid-form`, `lookup-view`, `options`, `process`, `settings`, `table-view` and
  `workflow` compile. None uses an XSD 1.1 construct.
- **`profile.xsd` does not compile.** L20-21 declare attributes named `xmlns:xsi` and
  `xmlns:xsd`, which are not valid `xs:NCName` values. That is a defect in the schema, not
  in libxml2. DGF's own `docs/wiki/AI-Authoring/format-coverage.md:113` already puts
  `profile.xsd` outside Wave-1 validator scope.

### The JSON family: the dialect is not the whole story

`knowledge/schemas/MANIFEST.md` §2.1: the vendored `json/` set has **68 draft-04** schemas
(generated by `SchemaExporter` via NJsonSchema) and **1 draft-07**; `standalone/` is all
draft-07. The dialect is chosen per file from its own `$schema`.

Across the 72 JSON files, the validation keywords in use are few: `type`, `$ref` (1,286
local, 1 external), `additionalProperties`, `properties`, `oneOf`, `items`, `enum`,
`format`, `required`, `minLength`, `allOf`, `pattern`, `not`, `if`/`then`, `minimum`,
`maximum`, `const`, `anyOf`, `minProperties`, `propertyNames` and `patternProperties`.
`format` values include the non-standard `int32`, `int64`, `float` and `guid`.

**NJsonSchema's inheritance does not survive a spec-compliant validator.** DGF's MCP
validates JSON with JsonSchema.Net 7.3.4 (`src/Tools/dgf-mcp/DgfMcpServer.csproj:54`).
`src/Tools/dgf-mcp/Services/SchemaValidationService.cs` L157-176 records why it deletes
`$schema` and strips **every** `additionalProperties: false` before compiling:

> NJsonSchema models inheritance as `"allOf": [ { "$ref": "#/definitions/Base" }, { properties: …, additionalProperties: false } ]` …
> each allOf branch evaluates independently, so the derived branch (with
> additionalProperties: false) rejects every property the base declares.

The comment attributes the merged reading to draft-04. The draft-04 specification does not
say that: `additionalProperties` considers only `properties` and `patternProperties` in the
**same** schema object, in every draft. So this is not a draft-04-versus-2020-12 problem.
It is an **NJsonSchema-semantics** problem, and any spec-compliant validator — including
`jsonschema`'s draft-04 validator — rejects configurations that are valid. The consequence
for DGF's MCP is that it rejects **no** unknown property at all.

## Decision

**Milestone 8's validators are Python 3.9+ scripts using `lxml` for the XSD family and
`jsonschema` for the JSON family, installed by the user from a pinned requirements file.
The dependency is confined to the validators, and a missing dependency is reported, never
passed.**

1. **Interpreter floor: Python 3.9.** It is what macOS ships, and the validators must run
   on the interpreter a DGF developer already has.
2. **XSD family: `lxml.etree.XMLSchema`**, against the vendored XSDs. Same libxml2 engine as
   `xmllint`, so the 8-of-9 compile result above is the validator's result.
3. **JSON family: `jsonschema`**, choosing `Draft4Validator` or `Draft7Validator` from each
   file's `$schema`. Never one dialect for the whole set.
4. **NJsonSchema inheritance is handled by a deterministic schema pre-pass, not by stripping.**
   Where an `allOf` combines a `$ref` with a sibling object that sets
   `additionalProperties: false`, the pre-pass validates against the **merged** property set
   (union of `properties`, union of `required`) with `additionalProperties: false` applied to
   the union. That is the reading NJsonSchema intends. Unknown properties are then rejected,
   which DGF's MCP does not do. The pre-pass has its own fixtures — one inherited-property
   pass, one unknown-property fail — and is the part of the validator most likely to be
   wrong, so it is tested first.
5. **`format` is annotation-only** in the first version. The non-standard formats (`int32`,
   `int64`, `float`, `guid`) are not asserted, and the gate says so in `checks_run` rather
   than implying they were checked.
6. **Pinned and documented, never auto-installed.** Exact versions with hashes go in
   `scripts/requirements.txt`, created in milestone 8 against the current PyPI releases and
   checked there for Python 3.9 support. `docs/getting-started.md` documents the install
   command. Nothing in the plugin runs `pip` on the user's behalf.
7. **A missing dependency is exit `3`** (usage error, per `.ai-factory/rules/base.md`), with
   the exact install command in the message. A validator that cannot import its engine never
   exits `0`.
8. **The existing scripts stay stdlib-only.** `doctor.py` and `check_knowledge_stamps.py`
   take no dependency, so `/dgf-doctor` can run before anything is installed. The doctor gains
   a dependency probe that reports whether the validators can run; it does not install
   anything either.
9. **`profile.xsd` is not validated.** It is vendored for reference and drift, reported as
   uncompilable, and excluded from the XSD validator with that reason stated. This matches
   DGF's own Wave-1 scope.

## Alternatives considered

- **A .NET 10 file-based app** (`dotnet run validate.cs`) using `System.Xml` for XSD, the
  engine behind DGF's `XsdValidationService`, and NJsonSchema's own validator. It would have
  had the closest parity with DGF and native NJsonSchema semantics, on an SDK every DGF
  developer already has. Not chosen. It costs a NuGet restore on first run (network once),
  a slow cold start on every gate, and a second runtime next to the Python scripts the
  plugin already has.
- **Python stdlib plus `xmllint`**, with this plugin's own JSON validator for the roughly 20
  keywords in use. Zero installs on macOS. Rejected: it makes this plugin the owner and sole
  tester of a JSON Schema implementation, and `xmllint` is not installed by default on many
  Linux images (`libxml2-utils`).
- **Node with `ajv` and `ajv-draft-04`**, plus `libxmljs` or a shell-out to `xmllint`.
  Rejected: it needs an `npm install` step too, has the same NJsonSchema-inheritance problem,
  and adds a Node dependency tree to a plugin whose scripts are otherwise Python.
- **Do what DGF's MCP does** — strip `$schema` and every `additionalProperties: false`.
  Rejected. It is simple and matches the MCP exactly, but it gives up unknown-property
  rejection, which is the most useful check for AI-generated configuration. This plugin's
  gate must not be weaker than a careful review.

## Consequences

### Positive

- **Standard, well-tested engines for both families.** No hand-written schema validator.
- **The JSON gate is stricter than DGF's MCP.** Unknown properties are rejected, which the
  MCP gave up (`SchemaValidationService.cs` L169-172).
- **`/dgf-doctor` keeps working with nothing installed**, and can say exactly what is missing.

### Negative

- **Every user must install two packages** before the validators run. The plugin cannot do
  it for them, so the first gate a new user runs fails with exit `3` until they do.
- **Stricter than the MCP means disagreement with the MCP.** A configuration the MCP accepts
  may fail here on an unknown property. That is intended, but it has to be explained every
  time it happens, and a wrong pre-pass would make it a false positive.
- **The inheritance pre-pass is ours to maintain.** If NJsonSchema changes how it emits
  inheritance, the pre-pass silently stops matching; its fixtures are the only guard.
- **`profile.xsd` stays unchecked** until DGF fixes the schema.
- **Python 3.9 is end-of-life upstream.** Holding the floor there keeps the macOS system
  interpreter usable, but pinned packages will eventually drop 3.9, and the floor will have
  to move.

### Follow-ups

- Milestone 8: create `scripts/requirements.txt` with exact versions and hashes, confirm each
  supports Python 3.9, and document the install in `docs/getting-started.md`.
- Milestone 8: build the NJsonSchema inheritance pre-pass with its fixtures before any other
  JSON check.
- Milestone 8: add the dependency probe to `doctor.py` (stdlib-only; it reports, never installs).
- Report upstream to the DGF team: `profile.xsd` L20-21 is invalid XSD; and
  `SchemaValidationService.cs` L157-176 attributes to draft-04 a merge the draft-04
  specification does not define.
- **What would reverse this:** a requirement that the gate match DGF's MCP exactly, or
  evidence that the pre-pass cannot reproduce NJsonSchema's semantics. Either points to the
  .NET alternative above.
