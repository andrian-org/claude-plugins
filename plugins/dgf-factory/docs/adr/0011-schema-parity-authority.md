# 0011 — Resolve the schema family first; `format-coverage.md` is the only runtime-parity authority

**Status: proposed.** This rule has been in force since the "Verified DGF Fact Base" milestone
(2026-09-19) as a contract in [DGF Schemas](../dgf-schemas.md) and a rule in `AGENTS.md`, but no
ADR records it or says when it must be revisited. It must be accepted **before milestone 8's
parity check is written**, because that check hard-codes the authority this ADR names.

## Context

Read on **2026-09-23**. DGF paths are relative to the DGF repository root at `aa1d5c4c2`.

**DGF has two schema families, and the runtime does not read both for every component.**
The modern family is JSON component configuration, validated by the JSON schemas under
`src/Tools/dgf-mcp/Schemas/Json/`. The legacy family is XML, validated by the XSDs under
`src/Tools/dgf-mcp/Schemas/XSD/`. Both are vendored under `knowledge/schemas/`.

A passing schema validation does **not** prove the runtime reads that format:

- `docs/wiki/AI-Authoring/format-coverage.md:60` — **ProcessFlow**: *"Schema exists but runtime
  parses legacy `_process.xml`."*
- `format-coverage.md:86` — **Workflow**: *"Schema exists but runtime parses `_workflow.xml`
  exclusively."*
- `format-coverage.md:45` — **Form**: the runtime reads JSON, but *"most consumer apps still
  author `_form.xml`"* because the JSON path lacks parity for custom cells, `<slavegrid>` and some
  `<binding>` patterns.
- `format-coverage.md:103` — the five legacy artifact types (form, workflow, process, settings,
  view) *"have no JSON equivalent today. The runtime reads only XML."*

**The generation policy is explicitly temporary.** `format-coverage.md:138`: *"Wave 1 policy:
AI generates XML for all five legacy artifact types, regardless of partial JSON parity."*
`format-coverage.md:143`: *"This will change in Wave 1.5 once the capability matrix lands as an
MCP tool."* Line 15 names the trigger: the page being caught stale by DGF's
`/dgf-freshness-audit`.

**No other source is authoritative for parity.** The JSON schemas are generated by
`SchemaExporter` from configuration classes, so a schema exists for every class whether or not
the runtime reads that format. The MCP offers no parity query today. DGF's
`docs/schemas/` holds only three hand-authored standalone contracts, not the generated set.

**Where the rule already lives in this plugin:**

- `AGENTS.md` §"Agent Rules" — *"Both schema families, always — and check parity."*
- `.ai-factory/rules/base.md` §"DGF Schema Handling" — resolve the family before parsing,
  unknown family is exit `3`, and a schema-valid config the runtime does not read is exit `2`.
- `knowledge/composition-specs.md` stamps the XML-always policy as a **policy** fact with
  `review_date: 2026-09-22`, per [ADR 0008](0008-version-gating-revised.md) §2.
- [ADR 0005](0005-default-team-rules.md) rule 1 ships XML-always as a scripted default.

## Options

### A. `format-coverage.md` is the sole authority, vendored and reviewed — recommended

Every parity claim cites a `format-coverage.md` row. The page is tracked by digest like any
other source, and the XML-always policy is reviewed on every re-vendor through the
`review_date` on `knowledge/composition-specs.md`.

### B. Wait for the MCP capability matrix

Query parity from the MCP once Wave 1.5 lands. It is the right long-term answer, but it does
not exist, has no date, and [ADR 0006](0006-process-verification-revised.md) §3 already rules
out a network dependency in the gate.

### C. Derive parity from the runtime

Treat a format as supported when a runtime deserializer for it exists. It is exact in
principle, but it is a code-reading exercise per component, and `format-coverage.md`'s Form row
shows that "the runtime can parse it" and "you should author it" are different questions.

## Decision

**Recommended, not yet accepted:**

- **Every task touching component configuration resolves the schema family before parsing,
  and handles both families.** An unknown family is exit `3`; a document valid against neither
  family is exit `1`.
- **A schema pass is never reported as runtime support.** A config valid in a family the
  runtime does not read for that component is exit `2`, `schema-valid but not runtime-supported`.
- **`docs/wiki/AI-Authoring/format-coverage.md` is the only authority for runtime parity.** It is
  cited per row and tracked by digest.
- **XML-always for the five legacy artifact types holds until DGF's Wave 1.5.** Its
  `review_date` is renewed on every re-vendor. A change to the page's digest, or the capability
  matrix appearing as an MCP tool, reopens this ADR.

## Alternatives considered

Options B and C above. Also rejected: **default to JSON when the family is ambiguous.** It makes
every legacy XML file look like malformed JSON, which is the failure `docs/dgf-schemas.md` was
written to prevent.

## Consequences

### Positive

- The rule the plugin already follows gets a decision record and a revisit trigger.
- Parity claims become citable and drift-checked instead of recalled.

### Negative

- The authority is a human-maintained wiki page. When it is stale, this plugin is stale with it,
  and only the digest tells anyone.
- XML-always is scripted (ADR 0005 rule 1), so the Wave 1.5 change will be disruptive by design.

### Follow-ups

- **Accept, amend or reject before milestone 8's parity check is written.**
- On acceptance, cite this ADR from the `AGENTS.md` rule and from `.ai-factory/rules/base.md`
  §"DGF Schema Handling".
- No new tracking is needed. `docs/wiki/AI-Authoring/format-coverage.md` is already a stamped
  `sources` entry, with its `sha256`, in `knowledge/component-catalogue.md`,
  `knowledge/composition-specs.md` and `knowledge/naming-conventions.md`, so milestone 8's drift
  check covers it as soon as it reads those stamps.
