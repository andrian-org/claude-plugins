# DGF Schemas — JSON and XSD

DGF supports **two configuration formats**, because it still runs systems written against
the older one. Modern components are configured in JSON; five legacy artifact types are
still authored as XML. Both have committed, machine-checkable schemas, and both are served
by the DGF documentation MCP through separate tool families.

Anything in this plugin that validates a configuration, generates a component, or resolves
a component contract must handle both. Handling one and failing open on the other is a
defect, not a limitation.

> **Provenance.** Read from the DotGov Framework repository and the live DGF MCP on
> **2026-09-18** and **2026-09-19**. Re-verify before relying on a count or a parity claim;
> the parity data in particular is a living document on the DGF side.

---

## 1. Two parallel reference pipelines

Both families are generated by `src/Tools/SchemaExporter` from C# sources, committed into
`src/Tools/dgf-mcp/Schemas/`, and refreshed by `src/Tools/dgf-mcp/sync-schemas.sh`.

| Aspect | Modern JSON config | Legacy XML grammar |
|---|---|---|
| C# source | `IComponentConfiguration` classes | `DGF.Domain.Data.Form.*` classes |
| Exporter | `SchemaExporter.ExportWith_NJsonSchema` | `SchemaExporter.LegacyXmlReferenceExporter` |
| Output | `*.schema.json` | `form.reference.json` (plus hand-authored `*.xsd`) |
| Committed copy | `src/Tools/dgf-mcp/Schemas/Json/` | `src/Tools/dgf-mcp/Schemas/XSD/` and `Schemas/XmlReference/` |
| MCP property tool | `get_component_property_reference` | `get_xml_property_reference` |
| MCP discovery tools | `list_available_json_schemas`, `get_json_schema_details` | `list_available_xsd_schemas`, `get_xsd_schema_details` |

Sources: `Schemas/Json/README.md`, `Schemas/XmlReference/README.md`,
`Services/SchemaIndexService.cs`, `sync-schemas.sh`.

## 2. Schema availability is not runtime parity

This is the fact most likely to cause a wrong result, so it comes before everything else.

**A component can have a JSON schema while the runtime still reads only XML.** The
authority is `docs/wiki/AI-Authoring/format-coverage.md` in the DGF repository — a living
document written so that AI agents can decide deterministically which format to produce.

Legend: `✓` supported · `◐` partial · `✗` not supported today.

| Component | JSON schema | Runtime parses JSON | Consequence |
|---|---|---|---|
| `Workflow` | ✓ | **✗** | Runtime parses `_workflow.xml` exclusively. Largest remaining migration. |
| `ProcessFlow` | ✓ | **✗** | Runtime parses legacy `_process.xml`. JSON path planned for Wave 2/3. |
| `Form` | ✓ | **◐** | JSON path lacks parity for custom cells (`control_xxx`), `<slavegrid>` (EditableGrid) and some `<binding>` patterns. |
| `Booking` | ✓ | **◐** | Booking workflow still triggers XML workflow steps. |
| `CorporateAccount` | ✓ | **◐** | Reads JSON; some validation paths still XML-only. |
| `EligibilityCriteria` | ✓ | **◐** | Reads JSON; underlying file-upload workflow still XML. |
| `PayComponent` | ✓ | **◐** | JSON config consumed; payment-gateway workflow still XML. |
| `Query` | ✓ | **◐** | Reads JSON for the filter panel; SP execution still uses legacy XML datasource configs in places. |
| `Uploader` | ✓ | **◐** | Reads JSON; large-file workflow and virus scan still XML. |

**The worked consequence:** a `Workflow` configuration can validate cleanly against
`WorkflowConfiguration.schema.json` while the runtime never reads that JSON. A validator
that reports success on that basis is producing a false positive. Family resolution is
necessary but not sufficient — parity must be checked too.

`format-coverage.md` is scheduled to be promoted from a static page to an MCP-served
capability matrix in **Wave 1.5**. Until then it must be read as a file.

## 3. Current generation policy — asymmetric, and dated

Quoting `format-coverage.md` directly:

> Wave 1 policy: **AI generates XML for all five legacy artifact types**, regardless of
> partial JSON parity above.

The three stated reasons:

1. Runtime support is partial, and mixed-format services would fail in production.
2. eCouncil tooling expects XML on disk for every entity.
3. JSON form generation has its own correctness gaps (custom cells, `<slavegrid>`) until
   form parity matures.

The five XML-only artifact types, which have no JSON equivalent today:

| Artifact | XSD | Status |
|---|---|---|
| `_form.xml` | `form.xsd` | XML-only. Form JSON parity is partial — see §2. |
| `_workflow.xml` | `workflow.xsd` | XML-only. Largest remaining migration. |
| `_process.xml` | `process.xsd` | XML-only. |
| `settings.xml` | `settings.xsd` | XML-only. Entity field declarations. |
| `view.xml` (3 subtypes) | `table-view.xsd`, `lookup-view.xsd`, `grid-form.xsd` | XML-only. Three subtypes share the `<view>` root. |

`options.xsd` (legacy `<options>` lists) and `profile.xsd` (profile tree definitions) exist
but are explicitly **out of Wave-1 validator scope**.

> **This policy is temporary by design.** It changes in Wave 1.5, when the capability
> matrix lands as an MCP tool and agents route per feature. Treat the rule as current
> practice dated 2026-09, not as a permanent property of the framework.

## 4. Inventories and source-of-truth precedence

Three inventories exist and they disagree. Any count quoted without naming its inventory
will be wrong against the other two.

| Inventory | Count | What it counts |
|---|---|---|
| Live MCP `list_available_json_schemas` | **56** | Component types the deployed server actually serves |
| Repository `Schemas/Json/*.json` | **69** | Files committed in the repo |
| `format-coverage.md` | **66** | Components claimed JSON-ready |

The gap reconciles exactly:

```text
56  served by the live MCP
 4  $ref-only sub-schemas   (RowConfig, SectionConfig, InputGroupConfig, IDataSource)
 6  DataSource family       (Api, Code, Document, RawSql, StaticOptions, Table)
 1  stale artifact          (NumberConfiguration`1.schema.json)
 2  newer than deployed     (Carousel, SignaturePadSig100)
--
69  files on disk
```

`Carousel` and `SignaturePadSig100` are present in the repository and in
`format-coverage.md` but **absent from the live MCP** — the deployed server predates them.
The XSD side has no such drift: 9 in the repository, 9 on the live server.

### Precedence rule

| Question | Authority |
|---|---|
| What can a validator rely on offline and deterministically? | The **vendored copy** in `knowledge/schemas/` |
| What does production actually serve right now? | The **live MCP** |
| Does the runtime read this format for this component? | **`format-coverage.md`** |

The deployed MCP can lag the repository. The schema ledger,
`provenance/knowledge/schemas/MANIFEST.md`, therefore records the DGF **commit SHA** the
vendored set was taken from, so the vendored set's position
relative to the deployed server is always knowable rather than assumed.

## 5. Correspondence map — XSD to JSON

The families are **not** two encodings of one model. Some concepts exist in only one.
Verified against `format-coverage.md`.

| XSD | Root element | JSON counterpart | Status |
|---|---|---|---|
| `form.xsd` | `form` | `FormConfiguration.schema.json` | True pair. Both have dedicated validators. |
| `workflow.xsd` | `Workflow` | `WorkflowConfiguration.schema.json` | True pair. Runtime is XML-only. |
| `process.xsd` | `Process` | `ProcessFlowConfiguration.schema.json` | Pair. Runtime is XML-only. |
| `table-view.xsd`, `lookup-view.xsd`, `grid-form.xsd` | `view` | — | No single JSON counterpart. Three subtypes share the `<view>` root. |
| `settings.xsd` | `entity` | — | None. Entity field declarations. |
| `options.xsd` | `options` | — | None. Legacy `<options>` lists; out of Wave-1 scope. |
| `profile.xsd` | `Tree` | — | None. Profile tree definitions; out of Wave-1 scope. |

> **Do not infer a counterpart from a filename.** `options.xsd` looks like it should pair
> with `StaticOptionsDataSource.schema.json`. It does not — it is the legacy `<options>`
> list grammar, an unrelated concept. Use this table; when a row says none, there is none.

## 7. Family detection contract

A consumer resolves the family **before** parsing:

| Signal | Family |
|---|---|
| XML declaration or a known XSD root element | XSD |
| Parses as a JSON object | JSON |
| Neither, or both plausible | **Unresolved** |

Contract, using the project exit codes from `.ai-factory/rules/base.md`:

| Outcome | Exit | Behaviour |
|---|---|---|
| Family resolved, valid, runtime parses this family | `0` | Success. |
| Family resolved, valid, runtime does **not** parse this family | `2` | Warn `schema-valid but not runtime-supported`, naming the component and the format the runtime expects. |
| Family resolved, invalid against that family's schema | `1` | Blocked. Report findings verbatim. |
| Valid against neither family | `1` | Blocked. Report which families were attempted. |
| Family unresolved or ambiguous | `3` | Usage error. **Never** fall back to JSON. |

Silently defaulting to JSON is the failure mode this contract exists to prevent: it makes
every legacy XML configuration look like malformed JSON rather than a different format.

## 8. JSON resolver irregularities

`Services/SchemaIndexService.cs` documents three cases the obvious
`<X>Configuration.schema.json` glob does not cover. A resolver must reproduce this
behaviour rather than globbing.

- **Standalone allow-list.** Cross-cutting contracts that are not per-component configs are
  registered by exact name. Today: `componentValidator.schema.json`.
- **DataSource discriminators.** Files are named `<Kind>DataSource.schema.json`, and an
  authored DataSource names no schema at all — it carries a lowercase discriminator
  (`table`, `rawsql`, `static`) that the engine reads to pick a class. The mapping mirrors
  `src/Core/DGF.DataSources/JsonConverters/DataSourceConverter.cs`: nine discriminators,
  six schemas. Lookup is case-insensitive.
- **`$ref`-only sub-schemas.** `RowConfig`, `SectionConfig`, `IDataSource` and
  `InputGroupConfig` are fragments, not component types, and must never be surfaced as
  components. This is why the glob is deliberately narrow rather than `*.schema.json`.

## 9. Vendoring contract

Schemas are **vendored, not read across the filesystem** — a validator that reaches outside
the plugin breaks the moment the plugin is installed elsewhere. The complete set is
vendored: all committed JSON schemas, all 9 XSDs, and `XmlReference/form.reference.json`.
Roughly 3.5 MB. What the set holds is
[`knowledge/schemas/MANIFEST.md`](../knowledge/schemas/MANIFEST.md), which ships. Where each
file came from, from which commit, with its digests, is the maintainer-only ledger
[`provenance/knowledge/schemas/MANIFEST.md`](../provenance/knowledge/schemas/MANIFEST.md).

```text
knowledge/schemas/                      # shipped
├── MANIFEST.md        # DGF version, vendored date, per-file dialect and membership
├── json/              # generated *.schema.json from Schemas/Json/
├── xsd/               # the 9 *.xsd plus form.reference.json
└── standalone/        # hand-authored contracts from DGF docs/schemas/

provenance/knowledge/schemas/MANIFEST.md   # not shipped — commit SHA, upstream + shipped sha256
```

**The shipped copies are not byte-identical to upstream.** A shipped file carries no DGF
repository path ([ADR 0012](adr/0012-no-dgf-paths-in-shipped-files.md)), and DGF's own schema
text contains some. `tools/vendor_schemas.py` rewrites them as it copies the set in: a
`docs/wiki/<page>` link becomes `get_doc_page('<page>')`, and any other DGF path is cut to its
file name. Nothing else changes. At the 2026-09-23 vendor that touched 61 of 82 files.

Three hazards are verified, not theoretical. Each has a required mitigation.

### 9.1 Case collision — silent data loss

`docs/schemas/dataFetcherConfiguration.schema.json` (hand-authored, draft-07, 5.6 KB) and
`Schemas/Json/DataFetcherConfiguration.schema.json` (generated, draft-04, 53 KB) differ
only by the case of the first letter. On a case-insensitive filesystem — the macOS default
— writing both into one directory leaves **one file**, with no warning and no error.

**Mitigation:** the hand-authored contracts live in `standalone/`, never beside the
generated set. Never flatten the two into one directory.

### 9.2 Mixed JSON Schema dialects

Generated schemas declare `http://json-schema.org/draft-04/schema#`. The hand-authored
contracts declare `draft-07`.

**Mitigation:** select the validator dialect from each file's own `$schema`. Never assume
one dialect for the set. `MANIFEST.md` records the dialect per file so the mix is visible
without opening every schema.

### 9.3 Shell-hazardous filename

``NumberConfiguration`1.schema.json`` contains a backtick — a C# generic-arity marker that
leaked through the exporter. Unquoted in a shell, it triggers command substitution. The
file is also stale and unserved by the live MCP.

**Mitigation:** quote every schema path in every script. Do not special-case this one file;
quoting is the rule.

### 9.4 What the two manifests record

The shipped `knowledge/schemas/MANIFEST.md`:

- DGF version and vendored date — the stamp for the set, since the schemas are not Markdown
  and cannot carry one of their own
- Per-file `$schema` dialect
- Any file present in the vendored set but not served by the live MCP, and the reverse

The maintainer ledger `provenance/knowledge/schemas/MANIFEST.md`, whose frontmatter only
`tools/vendor_schemas.py` writes:

- DGF commit SHA the set was vendored from (`dgf_commit`)
- Per file: the upstream path, the upstream `sha256`, the vendored path, and the shipped
  `sha256`. The drift check compares the upstream digest against a DGF checkout.
  `tools/check_knowledge_stamps.py` compares the shipped digest against the shipped file, so
  a hand edit to a vendored schema fails without any checkout.
- Which files came from `Schemas/Json/`, which from `Schemas/XSD/`, and which from the
  hand-authored `docs/schemas/` contracts
- The rewrite rules and what each re-vendor changed

## 10. Re-vendor and drift process

DGF's own upstream flow, which this plugin mirrors rather than reinvents:

```bash
dotnet run --project src/Tools/SchemaExporter
bash src/Tools/dgf-mcp/sync-schemas.sh
# commit the changed Schemas/Json/*.schema.json and Schemas/XmlReference/
```

On the DGF side, `/dgf-freshness-audit` catches a forgotten sync and blocks the release.
**That audit does not see this plugin.** Re-vendoring here is therefore a deliberate act:

1. Re-run the upstream flow in the DGF repository, or confirm it is already current, and
   commit it — the vendoring tool refuses a DGF tree with uncommitted schema changes.
2. `python3 tools/vendor_schemas.py <dgf-root> --dry-run`, then without `--dry-run`. It
   copies the sets into `knowledge/schemas/{json,xsd,standalone}/` respecting §9.1, rewrites
   DGF paths, and regenerates the ledger's frontmatter and the shipped manifest's stamp.
3. Update the ledger's prose and the shipped manifest's prose for any dialect or membership
   change.
4. Re-read `format-coverage.md` and update any parity claim this plugin repeats.

The ledger's §4 has the full procedure. Never automate step 2 on a schedule. A vendored set that changes without a recorded
decision is worse than one that is knowingly old.

## 11. Adjacent, and explicitly out of scope

DGF also ships a **canonical service spec schema** (v0.9, provisional) at
`docs/wiki/AI-Authoring/spec-schema-v0.9.md`, with structured lint rules at
`spec-lint/universal-rules.md`. The MCP serves both through `get_spec_schema` and
`get_spec_lint_rules`. It is the input contract for AI-driven service generation: an agent
fills in the template, a spec-doctor skill lints it, downstream tools consume the result.

That is a **service-level** spec, not a component configuration schema — a different layer
from everything above. It is named here so a later reader can see it was considered and
deliberately left out, rather than missed. It likely deserves its own treatment before any
scaffolding or greenfield skill is written.
