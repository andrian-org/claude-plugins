# Interactive setup skipped the line prompt once a receipt existed; known-good passed at the wrong tag

**Date:** 2026-11-05 01:00
**Files:** cli/commands/setup.mjs, tools/run_known_good.py, tests/cli/lines.test.mjs, tests/test_run_known_good.py, docs/dgf-lines.md
**Severity:** medium

## Problem

Two findings from `/aif-verify` on `feature/dgf-version-packs`:

1. Re-running `dgf-factory setup` on a terminal, with no `--dgf-line` / `--dgf-version`, never asked which DGF
   line to install once the project had a receipt. It silently kept the receipt's `dgfLine`. ADR 0036 §3 says
   "Interactive setup asks, with that default", and the plan's selection table row reads "none, interactive →
   prompt; default = receipt → config → current". An interactive re-run could not switch lines; only a flag could.
2. `tools/run_known_good.py --pack 1.3` against a checkout at tag `1.3.1` printed `CLEAN` with no warning. Seen live:
   `dgf_lines.py status` moves the line's cache to the newest tag, so the next known-good run checked the 1.3.0
   pack against 1.3.1's samples and passed. `check_drift.py` warns `VERSION_MISMATCH` for the same case.

## Root Cause

1. `chooseLine` short-circuited on the selector's source: `fallback.source === 'receipt' ? fallback : askLine(…)`.
   The receipt was treated as an answer rather than a default — unlike the harness prompt beside it, which asks
   on every re-run with "Enter keeps" the receipt's selection. No test drove a re-run through a scripted terminal,
   so the only interactive test (no default at all) passed and the receipt branch was never exercised.
2. The plan's Interfaces table said the tool "checks the checkout's tag is the pack's", but the implementation only
   *printed* the tag in the header and downgraded stale-exception checks on a commit drift. The tag never fed the
   verdict, and there was no test, because the run itself needs a DGF checkout and the tests only covered parsing.

## Solution

1. `chooseLine` always calls `askLine` on a terminal; the selector's result (receipt → config → current) is the
   default `[Enter keeps …]`. A refusal (version below every pack) still has no default and still refuses on Enter.
   Regression test: "on a terminal the line is always asked, Enter keeping the receipt, then the config, then the
   current line" — failed before (no line prompt on the re-run), passes after; it also covers the config and
   current-line defaults and a typed switch that removes the old pack's own file.
2. New `version_mismatch(tag, pack_entry)` returns why the checkout is not the pack's release (another tag, or none;
   a `legacy` pin is exempt). `main` prints it as `WARN VERSION_MISMATCH` and counts it, so the verdict is
   `WARNINGS`. Tests over a synthetic tagged repo; checked live: CLEAN at 1.3.0, WARNINGS at 1.3.1.
3. The previous fix's `[FIX]` markers in code comments became plain comments; `[FIX]` stays only in the gated
   `log.debug` / `report.debug` traces. `docs/dgf-lines.md` now says setup on a terminal always asks.

Checks: contract check CLEAN (unittest 1480 OK, `npm test` 111/111), `tools/smoke_install.sh` CLEAN.

## Prevention

- A stored previous choice (receipt, config) is a **default**, never an answer: an interactive prompt still asks.
  Two prompts in one command must treat their previous values the same way.
- Every interactive row of a plan's combination table needs a scripted-terminal test that records the prompts
  asked, not only the final result — a skipped prompt still produces a plausible result.
- When an Interfaces table says a tool "checks" something, the check must reach the verdict (a WARN/ERROR line and
  the exit code). Printing a value in a header is not a check.
- A tool that runs against a cache another tool moves (`status` checks out the newest tag) must verify the cache's
  state itself rather than assume it.
