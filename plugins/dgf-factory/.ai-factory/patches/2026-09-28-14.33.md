# The writing skills' confirm rows assumed git and a well-formed file

**Date:** 2026-09-28 14:33
**Files:** skills/dgf-process/SKILL.md, skills/dgf-model/SKILL.md, skills/dgf-component/SKILL.md, skills/dgf-audit/SKILL.md, scripts/audit_root.py, tests/test_audit_root.py, tests/test_skill_contracts.py, docs/pipeline.md, docs/skill-authoring.md, docs/adr/0024-learning-loop-revised.md, .ai-factory/DESCRIPTION.md, .ai-factory/plans/feature-dgf-specific-skills.md
**Severity:** medium

## Problem

The seventh `/aif-verify` walked the three writing skills on two paths the Task 17 walk had missed.

- **No git.** `/dgf-process` modify and `/dgf-model` add/modify confirm over the whole root with
  `check_change.py --changed M:<file>` and no `--files`. With no base tree the script counts every
  finding as new. So an old unresolved `extract` in an untouched `webasm` entity gave exit 1, and the
  row "one in a file this skill did not write → STOP" stopped the skill after the file was written.
  Any estate that already holds an error — DGF's samples hold 109 — made those modes unfinishable.
- **A malformed file.** A file with no XML declaration that does not parse, or JSON cut short, makes
  `validate_process.py`, `validate_config.py` and `resolve_components.py` exit 3 with
  `FAMILY_UNRESOLVED`. Every confirm row for exit 3 said "STOP — a missing dependency's install
  command", so the skill left its own broken file on disk. `/dgf-model` inspect read the same code as
  "not an entity's XML" and skipped `validate_model.py`, which reports `XML_MALFORMED` on that file.
- **Smaller issues.**
  - `audit_root.py --app a --reach <b's file>` printed `REACH:` and nothing for any application.
  - Two lists of unchecked references left out `CreateRecord` and `StateProcess` START/INFO.
  - Some skill facts were uncited, or cited only to an ADR, which is not shipped.
  - "the plan" had dropped out of the three writing skills' patch sentence.
  - `DESCRIPTION.md` gave a stale drift count and called `/dgf-process` "proposed".
  - ADR 0024's status paragraph understated what it restates.
  - `pipeline.md`'s scripts column omitted `check_override.py`.

## Root Cause

- **The exit rows were written from the happy path of each call.** Exit 3 was read as "the call is
  wrong", its meaning for the scripts' own usage errors. But `FAMILY_UNRESOLVED` is a usage code about
  a *file*, and one a skill's own output can produce. The audit already knew this: `in_the_root()`
  demotes the same code to a root defect. The skills were written without that mapping.
- **ADR 0018 §5's "stricter, never looser" was applied without asking what it costs the caller.** For
  the gate, counting every finding as new is right. For a skill that must decide whether *its* write
  broke something, it removes the only signal it has. `/dgf-fix` and `/dgf-implement` avoid the
  problem by narrowing with `--files`. The new skills could not narrow, since ADR 0014 §2 needs the
  whole root, so they needed a baseline of their own, and none was written.
- **The walk ran where the author works: a git repository and well-formed files.** RULES.md rule 4
  was met to the letter — every skill was walked — but never with `git.enabled: false`, and never with
  a file the skill got wrong.

## Solution

- **A baseline before the write, without git.** `/dgf-process` modify (after its scope check) and
  `/dgf-model` add/modify now run the same whole-root `check_change.py` before the write, and keep its
  `ERROR` and `WARN` lines. After the write, a finding the baseline also holds — same code, file and
  message, whatever its line, as `lib/baseline.py` keys it — is pre-existing. Walked in a no-git root:
  - a harmless edit now continues, where it stopped before;
  - removing a field a form binds still reports the new `MODEL_CELL_UNBOUND`, so the cross-file catch
    stays.
- **`FAMILY_UNRESOLVED` routed as the file's defect.**
  - After a write: correct it within the same 3 attempts. The message says whether the file is not XML
    or has a root no XSD reads.
  - In inspect and validate: relay it and carry on.
  - Only `DEPENDENCY_MISSING` and true usage errors still STOP.
  - In the no-git baseline and change-check rows, one on another file is compared with the baseline.
- **`audit_root.reach_one`** prints `NOT AUDITED: <ws> — --app narrowed the audit to …` for a file whose
  application `--app` left out. It is traced with `report.debug`, and `/dgf-audit` and
  `docs/skill-authoring.md` describe the line.
- **Prose and docs.**
  - The references no validator checks are cited to `reference-graph.md` §1's `Checked by` column.
  - The skill facts now cite `knowledge/` (`reference-graph.md` §3, `permissions.md` §1 and §2.1,
    `data-model.md` §1, §3.2, §3.3, §4 and §5).
  - "the plan" is restored in the patch sentence.
  - `DESCRIPTION.md` has the right count, and describes `/dgf-process` as built.
  - ADR 0024 has a dated erratum, and its status paragraph now separates what it decides from what its
    text adds.
  - `pipeline.md`'s table and paragraph are complete.
  - The plan's notes record the walk, and why `list_components` is not in `/dgf-component`'s tools.
- **Tests.**
  - `test_audit_root` gains the narrowed-reach case. It failed before the fix and passes after it.
  - `test_skill_contracts.WritingSkills` pins both routing rules:
    - every exit-3 row after a validator runs on the written file names `FAMILY_UNRESOLVED` and
      "correct it";
    - every skill whose confirm runs over the whole root has a `--changed` run with no `--files`
      before its `Write` step.

    It asserts that exactly `dgf-model` and `dgf-process` were checked, so it cannot pass vacuously.
    Both mutants (the old exit-3 row, the baseline removed) fail it.
  - 874 tests pass; the doctor and the docs check are clean.

## Prevention

- **Walk every writing mode with `git.enabled: false` as well as with git.** A change check without a
  base tree behaves differently by design, and the skill's reading of its output must still let it
  finish.
- **Walk a write that goes wrong.** Feed the confirm step a file the skill could plausibly have
  mangled: no XML declaration, JSON cut short, a misspelt root. Then check which exit and code arrive,
  and what the row does with them.
- **Map exit 3 by code, not by number.** Before writing "exit 3 → STOP", list the codes the script can
  exit 3 with (`report.CODES`, plus `lib/`'s `rep.add` sites), and give each one its own action. A code
  about a file the skill wrote is the skill's to fix.
- **When a caller cannot narrow a check that has no baseline, it must take one itself.** Record the
  run before the change, and compare as `lib/baseline.py` does: by code, file and message, never by
  line.
- **Not yet fixed:** `/dgf-implement`'s task with `deletes` also runs the whole root without git and no
  baseline (its Step 3.4). Its exit-1 row acts only on files the task wrote, so it does not stop, but it
  cannot tell whether a removal broke another file. It is a candidate for the same baseline.
