# Generated templates paste titles unescaped, and a case-only table's second part still spoke

**Date:** 2026-09-27 21:40
**Files:** scripts/lib/model.py, scripts/lib/edges.py, scripts/lib/json_validate.py, scripts/resolve_components.py, scripts/audit_root.py, scripts/validate_model.py, knowledge/data-model.md, knowledge/reference-graph.md, provenance/knowledge/data-model.md, docs/adr/0023-dgf-specific-skills.md, docs/pipeline.md, skills/dgf-model/SKILL.md, skills/dgf-component/SKILL.md, tests/test_model.py, tests/test_validate_model.py, tests/test_audit_root.py, tests/fixtures/known-bad/model-view-title-unescaped/, tests/fixtures/known-bad/model-grid-title-unescaped/
**Severity:** medium

## Problem

The third `/aif-verify` on the DGF-specific-skills branch found one blocker, a regression the last fix
exposed, and a misclassified exit code:

- **The blocker.** A missing view, grid or form was called "generated", although the runtime throws when
  a field title holds `&`, `<` or `"` once read. `title="Name &amp; Surname"` gave
  `MODEL_REFERENCE_TEMPLATED` (exit `2`), where `LookUpViewManager` throws an `XmlException`.
  `knowledge/data-model.md` §3.4 even said a generated grid "always builds".
- **The regression.** The audit reported a case-only table's missing form as "the runtime generates a
  default", beside the table's own `CASE_ONLY_MATCH`. On Linux the table load throws first.
- **The exit code.** An unreadable vendored schema dialect — the plugin's defect — was demoted to exit `1`
  as a defect in the root.
- **Wording.** Several tables and docs named forms among `validate_model.py`'s references, and claimed a
  `settings.xsd` break exits `1`.

## Root Cause

- **The template was read as far as its preconditions, and not as far as its output.** The last fix read
  `GetXmlTemplate` for what it needs from the table (a `Text` field, a `uimask`). It did not follow the
  string it returns into `SaveXml`, where `XmlDocument.LoadXml` parses it. Every generator builds XML —
  the view with `string.Format`, the grid and the form with string interpolation — over names and titles
  XmlSerializer has already decoded, so an `&amp;` in the file
  is a bare `&` in the template. The failure sits one call past the function that was read.
- **"Restates its table" was defined by result type, not by what the loader does.** `restates_its_table`
  listed `Unresolved` and `AppDependent`, the two types that existed when it was written. A `CaseOnly`
  table is also missing on Linux, so the loader throws there too, but it was not listed. The gap stayed
  silent until the audit began reporting `template` edges.
- **One code carries two meanings.** `SCHEMA_UNSELECTABLE` is "no schema selects this file" at five
  sites, and "a vendored schema's dialect is unreadable" at two. A rule keyed on the code alone cannot
  tell them apart.
- **A test fixture decided a doc row.** The row for `validate_config.py` exit `1` described what a
  grammar break "should" do. `xsd.validate` turns every non-process grammar error into
  `XSD_LAGS_RUNTIME`.

## Solution

- **`model.py` rebuilds what each generator pastes, and parses it** with expat, as `SaveXml` does, each
  value inside a double-quoted attribute:
  - the view: the key, and the display field's name and title;
  - the grid: its one column, chosen as the runtime chooses it — the first `required` `Text` field
    besides the key, else the first `Text` field besides it, else the key;
  - the form: a row for each field that is `required` or required for the form and valid for it
    (`uimask` characters 2 and 4), and a hidden cell's title for each of the seven audit fields.

  A value that does not parse is `Unresolved(throws=True)`, which `validate_model.py` blocks on (views,
  grids) and the audit reports as throwing (forms). `entity_fields` now reads `title` and `required` (as
  an xsd:boolean), and `resolve_grid` gained the generation check it lacked. Values that parse once
  pasted (`&amp;amp;`, `&apos;`, `&gt;`), and fields a template does not use, stay harmless.
- **`restates_its_table`** also suppresses a `CaseOnly` table's second part. This removes the audit's
  wrong "generated" line and `validate_model.py`'s duplicate `CASE_ONLY_MATCH` on `extract-view`.
- **`json_validate.add_unknown_dialect` / `is_unknown_dialect`** are the one definition of the
  plugin-side `SCHEMA_UNSELECTABLE`. `resolve_components.py` and `json_validate` raise it through the
  helper. The audit keeps it at exit `3`, and still counts the file-side `SCHEMA_UNSELECTABLE` as a
  defect in the root.
- **Knowledge, provenance and the ADR 0023 erratum:**
  - `data-model.md` §3.2, §3.4, §3.6 and §4 state what each template pastes, and that nothing in the
    samples holds `&`, `<` or `"`.
  - `reference-graph.md` §1 lists the fourth `template` exception.
  - The ledger records the lines read.
  - The same-day erratum names all three ways a generated file fails.
- **Wording:**
  - the `validate_model.py` docstring;
  - `/dgf-model` :20, :90 and :119: `settings.xsd` breaks are exit `2`, and forms are not
    `validate_model.py`'s;
  - `/dgf-component` :121: exit `0` may carry `NOT RUN: form-cells`;
  - `pipeline.md` :327-328 and the paragraph under them.
- **Tests:**
  - 9 regression tests failed before the fix and pass after it.
  - One test guards against over-blocking, and passes either way.
  - Two new known-bad cases, `model-view-title-unescaped` and `model-grid-title-unescaped`.
  - Known-good counts are unchanged, since no sample title needs escaping.
  - Coverage added after the fix:
    - a generated form whose row title does not parse, end to end through the audit;
    - the view's fallback to the table's first field when the display field's name is `""`, tested both
      ways, so a check of the wrong field fails it.

## Prevention

- **Follow a generated string until something parses it.** A template function's output is an input to
  whatever consumes it. When a builder uses `string.Format` or interpolation, list every value it
  pastes and ask what the consumer does with `&`, `<` and `"`.
- **Encode "the loader throws first" by what the loader does, not by the result types that exist
  today.** When a new result type is added, re-check every predicate that enumerates result types.
- **A report that starts reporting a new class of findings re-opens every suppression rule** it
  depends on. Test the new class against each neighbouring status: case-only, app-dependent, dynamic.
- **When one finding code carries two meanings, give the rarer meaning one named helper and a
  predicate**, so a consumer never matches on message text in more than one place. Better still, give
  it its own code when the change is allowed.
- **Write an exit row from the script's code path, not from what the row ought to say.** Run the case,
  or read the function that assigns the code.
