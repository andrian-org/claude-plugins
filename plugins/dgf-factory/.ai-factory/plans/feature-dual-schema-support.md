## Original Request

DGF has two type of schemas, because it also support old type of configurations. so when we will validate configurations, or generate new components, or other tasks that will need component schemas they should be considered both types: JSON and XSD.
Architecture and other files must be updated.

## Background — Verified Evidence

### DGF ships two parallel, auto-generated reference pipelines

Both are generated by `src/Tools/SchemaExporter` from C# sources, committed into
`src/Tools/dgf-mcp/Schemas/`, and synced by `src/Tools/dgf-mcp/sync-schemas.sh`.

| Aspect | Modern JSON config | Legacy XML grammar |
|---|---|---|
| C# source | `IComponentConfiguration` classes | `DGF.Domain.Data.Form.*` classes |
| Exporter | `SchemaExporter.ExportWith_NJsonSchema` | `SchemaExporter.LegacyXmlReferenceExporter` |
| Output | `*.schema.json` | `form.reference.json` (+ hand-authored `*.xsd`) |
| Committed copy | `Schemas/Json/` — 69 files, 3.3 MB | `Schemas/XSD/` — 9 files, 112 KB; `Schemas/XmlReference/` — 48 KB |
| MCP property tool | `get_component_property_reference` | `get_xml_property_reference` |
| MCP discovery tools | `list_available_json_schemas`, `get_json_schema_details` | `list_available_xsd_schemas`, `get_xsd_schema_details` |

Source: `Schemas/Json/README.md`, `Schemas/XmlReference/README.md`,
`Services/SchemaIndexService.cs` (`_jsonSchemaIndex` / `_xsdSchemaIndex`, lines 9–38),
`sync-schemas.sh`.

### Schema availability is NOT runtime parity — the decisive fact

`docs/wiki/AI-Authoring/format-coverage.md` (living document, `last_updated: 2026-09-09`)
is DGF's authoritative JSON-vs-XML coverage matrix. It exists so that "**AI agents** can
decide deterministically … when to generate JSON vs. XML for a given artifact."

It establishes that a component can have a JSON schema while the runtime still reads only
XML. Legend: `✓` supported · `◐` partial · `✗` not supported today.

| Component | Schema | Runtime parses JSON | Consequence |
|---|---|---|---|
| `Workflow` | ✓ | **✗** | Runtime parses `_workflow.xml` **exclusively**. Largest remaining migration. |
| `ProcessFlow` | ✓ | **✗** | Runtime parses legacy `_process.xml`. JSON path planned Wave 2/3. |
| `Form` | ✓ | **◐** | JSON path lacks parity for custom cells (`control_xxx`), `<slavegrid>` (EditableGrid) and some `<binding>` patterns. `build_form_xml` exists to emit XML deterministically. |
| `Booking`, `CorporateAccount`, `EligibilityCriteria`, `PayComponent`, `Query`, `Uploader` | ✓ | **◐** | Read JSON, but an underlying workflow/validation path is still XML. |

**Therefore:** validating a `Workflow` config against `WorkflowConfiguration.schema.json`
can pass while the runtime never reads that JSON. A family-only validator is a
false-positive generator — exactly the defect class this plugin's architecture exists to
prevent.

### Current generation policy is asymmetric, not symmetric

Quoting `format-coverage.md` directly:

> Wave 1 policy: **AI generates XML for all five legacy artifact types**, regardless of
> partial JSON parity above.

Reasons given: runtime support is partial and mixed-format services would fail in
production; eCouncil tooling expects XML on disk for every entity; JSON-form generation
has correctness gaps until form parity matures. This changes in Wave 1.5, when the
capability matrix is promoted from a static page to an MCP tool.

The five XML-only artifact types, with no JSON equivalent today:

| Artifact | XSD | Status |
|---|---|---|
| `_form.xml` | `form.xsd` | XML-only (Form JSON parity partial) |
| `_workflow.xml` | `workflow.xsd` | XML-only. Largest remaining migration. |
| `_process.xml` | `process.xsd` | XML-only. |
| `settings.xml` | `settings.xsd` | XML-only. Entity field declarations. |
| `view.xml` (3 subtypes) | `table-view.xsd`, `lookup-view.xsd`, `grid-form.xsd` | XML-only. Three subtypes share the `<view>` root. |

`options.xsd` (legacy `<options>` lists) and `profile.xsd` (profile tree definitions)
exist but are explicitly **out of Wave-1 validator scope**.

### The MCP validation surface is split

| Family | Tools |
|---|---|
| JSON | `validate_component_config` (generic, by component type name), `validate_form_json`, `validate_workflow_json` |
| XML/XSD | `validate_form_xml`, `validate_workflow_xml`, `validate_process_xml`, `validate_settings_xml`, `validate_view_xml` (subtypes `table` \| `lookup` \| `grid`), `validate_xml_cross_references` |

`ValidateXmlTool.cs` also defines `validate_options_xml` and `validate_profile_xml`, which
are **not exposed by the live server** — consistent with those XSDs being out of Wave-1
scope. Do not document them as available.

Source: `Tools/ValidateComponentConfigTool.cs`, `Tools/ValidateXmlTool.cs`,
`Services/XsdValidationService.cs`, plus a live `list_available_*_schemas` call.

### Three inventories disagree — the deployed MCP is behind the repo

| Source | Count | What it counts |
|---|---|---|
| Live MCP `list_available_json_schemas` | **56** | Component types the deployed server actually serves |
| Local `Schemas/Json/*.json` | **69** | Files committed in the repo |
| `format-coverage.md` | **66** | Components claimed JSON-ready |

The gap reconciles exactly: `56 served + 4 $ref-only (RowConfig, SectionConfig,
InputGroupConfig, IDataSource) + 6 DataSource family + 1 stale (NumberConfiguration\`1)
+ 2 newer-than-deployed (Carousel, SignaturePadSig100) = 69`.

`Carousel` and `SignaturePadSig100` are present on disk and in `format-coverage.md` but
**absent from the live MCP** — the deployed server at `dgf-mcp.dotgov.uk` predates them.
Any document that quotes a single schema count without saying which inventory it came from
will be wrong against the other two.

Live XSD count is **9**, matching the repo exactly — the XSD side has no drift.

### Vendoring hazards — verified, not theoretical

1. **Case collision (silent data loss).** `docs/schemas/dataFetcherConfiguration.schema.json`
   (hand-authored, **draft-07**, 5.6 KB) and `Schemas/Json/DataFetcherConfiguration.schema.json`
   (generated, **draft-04**, 53 KB) differ only by leading-letter case. Reproduced on this
   machine: writing both into one directory on macOS leaves **one** file — the draft-07
   content under the generated filename, with no warning.
2. **Mixed JSON Schema dialects.** Generated schemas declare
   `http://json-schema.org/draft-04/schema#`; the hand-authored contracts declare
   `draft-07`. A validator must select the dialect per `$schema` rather than assume one.
3. **Shell-hazardous filename.** `NumberConfiguration\`1.schema.json` contains a backtick
   (a C# generic-arity marker that leaked through the exporter). Unquoted, it triggers
   command substitution. It is also stale and unserved by the live MCP.

### Naming conventions are irregular on the JSON side

`SchemaIndexService.cs` documents three cases the default `<X>Configuration.schema.json`
glob does **not** cover:

- `StandaloneJsonSchemas` — an explicit allow-list (`componentValidator.schema.json`)
- The DataSource family — files named `<Kind>DataSource.schema.json`, selected at runtime
  by a lowercase **discriminator** (`table`, `rawsql`, `static`), mirroring
  `src/Core/DGF.DataSources/JsonConverters/DataSourceConverter.cs:25-51` (9 discriminators,
  6 schemas)
- `$ref`-only sub-schemas (`RowConfig`, `SectionConfig`, `IDataSource`, `InputGroupConfig`)
  which must **not** be surfaced as component types

Any resolver this plugin documents must reproduce that behaviour rather than globbing.

### Consequence for existing dgf-factory documentation

Every current document assumes a single JSON schema family, and all of them point at
`DotGovFramework/docs/schemas/` — which holds only **3 hand-authored standalone contracts**
(`componentValidator`, `dataFetcherConfiguration`, `eventBase`), not the generated set.
Note that only `componentValidator` is synced into the MCP set; `eventBase.schema.json` is
served by no MCP tool at all.

### Correction to existing dgf-factory claims

`.ai-factory/DESCRIPTION.md` and `docs/dgf-knowledge.md` state "No BPMN engine was found"
and conclude `/dgf-process` rests on an unconfirmed premise. The "no BPMN" statement is
correct; the inference is not. DGF ships formal, machine-checkable process and workflow
grammars — `process.xsd` (`Process` → `OnStart`, `States`) and `workflow.xsd` (`Workflow`
→ `Sequence`, `Input`) — which are state-machine-shaped rather than BPMN, and
`format-coverage.md` confirms both are the live runtime formats. Blueprint open question
#1 is answered.

## Refinement Notes (2026-09-19)

What the `/aif-improve` pass changed, so the delta is reviewable:

- **Reframed the feature.** The original plan treated JSON and XSD as two symmetric
  families to support equally. `format-coverage.md` shows the relationship is asymmetric:
  XML is the generation target for all five legacy artifact types today, and a JSON
  schema's existence says nothing about whether the runtime reads it. Task 1 now owns both
  the runtime-parity axis and the Wave-1 generation policy.
- **Added the source-of-truth precedence rule** after finding the live MCP (56), the repo
  (69) and `format-coverage.md` (66) disagree, and that the deployed server is behind.
- **Resolved all four `[assume]` correspondence rows**, and corrected one that was wrong:
  `options.xsd` is legacy `<options>` lists, not `StaticOptionsDataSource`.
- **Added two missing tasks** — `docs/getting-started.md` and `docs/skill-authoring.md`
  both carry the single-family/stale-path claims and nothing corrected them.
- **Fixed a false-positive check.** The absolute-path assertion would have failed on the
  anti-pattern rule that forbids absolute paths, and on the immutable Original Request.
- **Renumbered tasks 7–12** to keep dependency order readable. No task was completed at
  refinement time, so no `- [x]` state was disturbed.

## Risks

- **Runtime parity data is a living document.** `format-coverage.md` is maintained by hand
  and policed by `/dgf-freshness-audit` on the DGF side only. Every parity claim this
  plugin copies is a point-in-time snapshot; `MANIFEST.md`'s commit SHA is what makes the
  snapshot's age visible.
- **Wave 1.5 will invalidate the generation policy.** The "always XML" rule is explicitly
  temporary — it changes when the capability matrix becomes an MCP tool. Documents written
  now must date the policy so it is obviously revisable, not mistaken for a permanent fact.
- **Vendor-everything footprint and drift.** ~3.5 MB of schemas in the plugin, with no
  automatic drift detection on this side, and a vendored set that can be *ahead* of the
  deployed MCP. The re-vendor process in Task 1 is the only guard.
- **Correspondence map completeness.** The map is now evidence-backed, but three XSDs
  (`options`, `profile`, and the `view` subtype split) have no clean JSON counterpart and
  are out of Wave-1 scope. A later consumer that expects total coverage will be surprised.
- **Doc-only change.** Nothing here is enforced at runtime until the validators exist.
  Task 12's check is the sole mechanical guard against regression.
