# Provenance — `knowledge/schemas/MANIFEST.md`

Maintainer-only. Not shipped: `provenance/` is outside the directories `doctor.py` lists in
`SHIPPED_DIRS`. This ledger records where every file of the vendored schema set under
[`knowledge/schemas/`](../../../knowledge/schemas/MANIFEST.md) came from. The contract is
[ADR 0013](../../../docs/adr/0013-version-gating-provenance-ledger.md) §1.

The frontmatter is written by `tools/vendor_schemas.py`. **Never hand-edit it.** Each entry
records:

- `path` — the upstream path, relative to the DGF repository root;
- `sha256` — the upstream digest;
- `vendored` — the shipped path, relative to `knowledge/schemas/`;
- `shipped_sha256` — the digest of the shipped file.

The two digests differ only where §3's rewrite changed the file.

## 3. The path rewrite

[ADR 0012](../../../docs/adr/0012-no-dgf-paths-in-shipped-files.md) §4. Applied by
`tools/vendor_schemas.py`, in this order:

| Upstream text | Shipped text |
|---|---|
| `docs/wiki/<page>` | `get_doc_page('<page>')` — resolvable on the hosted DGF docs MCP |
| any other path matching `DGF_PATH_PATTERN` in `doctor.py` | its file name |

Nothing else in a schema changes. The tool refuses to write when a DGF path survives the
rewrite, or when a rewritten file no longer parses.

At the 2026-09-23 vendor, 61 files were rewritten:

- **60 JSON schemas**, three mentions each:
  - `docs/wiki/Components/Behavior/Validators.md` twice, which became
    `get_doc_page('Components/Behavior/Validators.md')`;
  - `docs/Components/Behavior/Events.md` once, which became `Events.md`.
- **`xsd/form.xsd`**, where one `src/Core/…/ComponentEvent.cs` comment became `ComponentEvent.cs`.

**The Events link is broken upstream.** `docs/Components/Behavior/Events.md` does not exist in
DGF. The page is `docs/wiki/Components/Behavior/Events.md`, and the MCP serves it as
`get_doc_page('Components/Behavior/Events.md')`. The rewrite keeps to its two rules rather than
guessing, so the shipped text says `Events.md`. Report the link to the DGF team. Once it is
fixed upstream, a re-vendor turns it into a `get_doc_page` call with no rule change.

## 4. Re-vendoring

Mirrors DGF's own flow; see `docs/dgf-schemas.md` §10. In the DGF repository:

```bash
dotnet run --project src/Tools/SchemaExporter
bash src/Tools/dgf-mcp/sync-schemas.sh
```

Commit that upstream first. `tools/vendor_schemas.py` refuses a DGF tree with uncommitted
changes under the schema folders, because the commit it records would not describe the files
it copied. Then, here, as a **deliberate act**, never on a schedule:

1. `python3 tools/vendor_schemas.py <dgf-root> --dry-run` reports what would change and
   writes nothing.
2. `python3 tools/vendor_schemas.py <dgf-root>` copies the set, applies §3, removes vendored
   files that are no longer upstream, and regenerates this ledger's frontmatter and the shipped
   manifest's stamp. Every path is quoted internally: one filename contains a backtick.
3. Update §1 above. If membership or dialects changed, update the shipped manifest's prose.
4. Re-read DGF's format-coverage page and update any parity claim under `knowledge/` that
   repeats it, together with that file's ledger digest.
5. Run `python3 tools/check_knowledge_stamps.py` and `bash tools/check-dual-schema-docs.sh`.

DGF's `/dgf-freshness-audit` catches a forgotten upstream sync and blocks the release.
**That audit does not see this plugin.** A vendored set that changes without a recorded
decision is worse than one that is knowingly old.
