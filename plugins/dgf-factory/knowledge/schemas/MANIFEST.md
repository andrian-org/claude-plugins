# Vendored DGF schema set — what it holds

This is the stamp for the schema files under `json/`, `xsd/` and `standalone/`. They are not
Markdown and cannot carry frontmatter of their own, so this file stamps them as a set, per
[`../README.md`](../README.md) §1. Structural fact class: stamp only.

Where each file came from — its upstream location, its upstream and shipped digests, and the
DGF commit it was copied at — is in the maintainer provenance ledger for this file, outside
the shipped tree (`../README.md` §1).

## 1. What was vendored

| Directory | What it holds | Files |
|---|---|---|
| `json/` | DGF's generated JSON component-config schemas — the set the MCP serves through `get_json_schema_details` | 69 |
| `xsd/` | DGF's legacy XML grammars (XSD 1.0), plus the XML grammar reference `form.reference.json` | 10 |
| `standalone/` | The three hand-authored standalone contracts, not the generated set | 3 |

**The shipped copies differ from upstream in one way.** Where DGF's own text names a path in
the DGF repository, the path is rewritten as the set is copied in, because a shipped file never
carries one ([ADR 0012](../../docs/adr/0012-no-dgf-paths-in-shipped-files.md)). A wiki link
becomes a `get_doc_page('<page>')` call that resolves on the DGF docs MCP, and a source-file
path is cut to its file name. Nothing else in a schema is changed, and every rewritten file
still parses.

### 1.1 Dialects

`json/` mixes **68 draft-04** (generated by `SchemaExporter` from `IComponentConfiguration`
classes) and **1 draft-07** (`componentValidator.schema.json`, hand-authored and synced in).
The `standalone/` contracts are all draft-07. Select the validator dialect from each file's
own `$schema`; never assume one for the set.

## 2. Membership deltas — what this set knows that the live MCP does not say

**11 files are present but not indexed by the MCP.** The MCP's `SchemaIndexService` globs
`*Configuration.schema.json` and adds exactly one allow-listed file,
`StandaloneJsonSchemas = ["componentValidator.schema.json"]`. Everything else in the generated
set is a `$ref`-only sub-schema, excluded so it does not surface as a bogus component type.
They are vendored anyway: a validator that resolves `$ref` needs them.

- `ApiDataSource.schema.json`
- `CodeDataSource.schema.json`
- `DocumentDataSource.schema.json`
- `IDataSource.schema.json`
- `InputGroupConfig.schema.json`
- `NumberConfiguration`
- `RawSqlDataSource.schema.json`
- `RowConfig.schema.json`
- `SectionConfig.schema.json`
- `StaticOptionsDataSource.schema.json`
- `TableDataSource.schema.json`

**One file is vendored twice, on purpose.** DGF's own schema sync copies the hand-authored
`componentValidator` standalone contract *into* the generated set, which is why it is the lone
draft-07 there. `json/componentValidator.schema.json` and
`standalone/componentValidator.schema.json` are byte-identical. Both are kept: `json/` must
remain a faithful mirror of the generated set, or the drift check cannot diff it.

**Only 1 of the 3 standalone contracts is synced upstream.** `dataFetcherConfiguration` and
`eventBase` exist only among DGF's hand-authored standalone contracts and are served by no MCP
tool.

**Case-collision pair.** `standalone/dataFetcherConfiguration.schema.json` (draft-07, 5.6 KB)
and `json/DataFetcherConfiguration.schema.json` (draft-04, 53 KB) differ only in the case of
the first letter. On a case-insensitive filesystem, one directory would silently hold one
file. The directory split is the mitigation; **never flatten them.**
